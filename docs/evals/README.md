# Evaluation

**Which model should this workload actually pay for?** Fifty-five hand-labelled
support tickets, four configurations of the same code path `/v1/triage` serves in
production, every figure below derived from the raw per-ticket outcomes.

## The finding

**The cheap model is not cheap.** `haiku` costs a seventh of `opus` per ticket
and gets the whole classification right 60.0% of the time against 74.5% — but the
number that decides the money is severity, which drives escalation: 70.9% against
87.3%. It also reports 0.94 mean confidence on the band where it is right 67.6% of
the time (ECE 0.277, roughly twice the next worst), so the automation gate that
was supposed to catch its mistakes waves them through. Cheaper per ticket, more
expensive per incident — the saving is real and it is paid for somewhere else.

**Thinking buys more than the next model tier does, for less.** `sonnet-thinking`
takes the best classification accuracy of the four (81.8%), the best severity
accuracy (89.1%) and the best calibration (ECE 0.111), and it does it for **less
than `opus`** — $9.89 per thousand tickets against $11.22, while `opus` scores
74.5%. Turning reasoning on is a setting; buying the flagship is a bigger bill for
a worse result here. That is the whole gateway's thesis in one row: the axis worth
tuning was not the model tier.

**Nobody is good at severity.** Category accuracy runs 87–96%; severity runs
71–89% and is the axis every configuration loses the most points on. That is a
*prompt* problem before it is a model problem: the rubric is what tells the model
that blast radius beats loudness. Which is what Phase 5 measures.

## The recommendation

**`sonnet` with adaptive thinking.** It is the best configuration on every quality
axis that matters — classification, severity, calibration, escalation misses — and
cheaper than the flagship it beats. The trade-off it accepts is latency: reasoning
tokens are generated before the answer, so its p95 is 13.5s against `opus`'s 9.7s.
For an asynchronous triage queue that is invisible; for a synchronous caller it
would not be, and then `opus` is the fallback at more money for less accuracy but a
tighter tail.

Two caveats that belong next to the numbers rather than in a footnote:

- **n = 55.** A one- or two-point gap here is noise, and these runs are not
  deterministic — a re-run moves the small numbers. `sonnet-thinking`'s ~4-ticket
  lead over `opus` on classification is modest but repeated; `haiku`-versus-the-
  rest is the only gap wide enough to act on without hesitation. (`sonnet`'s 24.9s
  p95 is a single slow request, not a property of the model — the kind of tail a
  55-ticket sample will show.)
- **The tickets were drafted by a Claude-family model** (see `app/evals/dataset.py`
  for the full provenance note). Their labels are derived from the written rules in
  the playbook and two thirds are adversarial by construction, but the residual
  bias is real: read any cross-vendor comparison with it in mind. There is no
  OpenAI key on the machine this was run on, so the cross-vendor comparison has
  not been made at all — the three `gpt-*` configurations are declared in
  `app/evals/runner.py` and are one credential away.

**Total spend for the sweep below: $1.62.**
