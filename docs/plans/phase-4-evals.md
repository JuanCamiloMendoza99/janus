# Phase 4 — Evaluation

**Goal.** Answer the question the whole gateway exists to make answerable: *for
this workload, which provider and model should we actually use?*

This is the phase that separates the project from a tutorial. Anyone can call two
APIs. Measuring which one to pay for is the engineering.

## Scope

### 1. Golden dataset

`evals/tickets.jsonl` — 40–60 support tickets with hand-labelled expected
`category`, `severity` and `next_action`. Requirements:

- Written by hand, not generated by a model. A dataset an LLM produced measures
  agreement with that LLM, not correctness.
- Deliberately includes hard cases: calm reports of critical outages, furious
  messages about trivia, tickets that look like billing but are access problems,
  and tickets with PII buried mid-body.

### 2. Runner

`scripts/run_eval.py` — runs the dataset through every configured
provider/model/effort combination and writes per-run results.

Metrics, per combination:

| Metric | Why it matters |
|---|---|
| Category / severity accuracy | Does it get the answer right |
| Escalation false-positive rate | Wrongly paging a human is the expensive error |
| PII recall | A missed PII flag is a compliance problem, not a quality one |
| p50 / p95 latency | What the user feels |
| Cost per 1000 tickets | The number a business decision is actually made on |
| Cache hit rate | Whether the caching investment paid off |
| Confidence calibration | Is low confidence actually correlated with being wrong |

### 3. Report

`scripts/report_eval.py` — a markdown table committed to `docs/evals/`, so the
comparison is versioned and its history is visible as models change.

## The point

The interesting result is rarely "the biggest model wins". It is usually
something like: *a cheaper model matches the expensive one on category but is
noticeably worse on severity, and severity is what drives escalation, so the
cheaper model costs less per ticket and more per incident.* That kind of
conclusion is what the whole gateway was built to produce.

Report honestly, including the cases where the cheap model wins and where the
expensive one is not worth its price.

## Risks

- **This phase spends real money.** Estimate the cost before running a full
  sweep — 50 tickets × 4 configurations × 2 providers adds up. Use the cost
  ledger the project already has; it exists precisely for this.
- Overfitting the playbook to the golden set. Hold out a slice and never look at
  it while tuning prompts.
- A 50-ticket dataset gives wide confidence intervals. Report the sample size and
  resist over-reading small differences.

## Verification

```bash
python scripts/run_eval.py --providers anthropic openai --out docs/evals/
python scripts/report_eval.py
```

Done when:

- [ ] The dataset is hand-labelled and covers the documented hard cases.
- [ ] Every metric above is reported per provider/model combination.
- [ ] The report is committed and the README links to it with the headline finding.
- [ ] The total spend of a full sweep is documented, so the reader knows what the
      comparison cost.
- [ ] The README states which configuration the project recommends **and why**,
      including the trade-off it accepts.
